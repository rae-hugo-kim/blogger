# 기술 글 문체 가이드 (해요체)

기술/개발 글의 문체 기준입니다. `categories`가 `에세이`/`리딩노트`/`특허`가 아닌 모든 글(기본값 `작업노트`)에 적용됩니다.
구조·SEO·정제 불변 규칙은 [`tone-guide.md`](tone-guide.md)(공통)를 따릅니다.

## 적용 대상

- 작업노트(만들고 부순 기록)와 기술 글 전반 (categories 미지정 시 기본값 `작업노트`)
- 황견적 개발일지
- fmkorea 연재 흔적이 있는 개발일지 (fmkorea.com 게시글 URL, 조회/추천 수 헤더)
- aiwitness가 참조로 달린 기술 글
- 단, 외부 글을 읽고 쓴 노트/단상 모음은 [`tone-note.md`](tone-note.md)(리딩노트)로 분류

## 문체

### 기본 어투

- **~해요/~거든요/~인데요** 체 (친근한 설명체)
- 딱딱한 논문체(~하다/~한다) 금지
- 독자에게 말 거는 느낌: "이걸 보면 아시겠지만", "한번 해볼까요?"

### 좋은 예 / 나쁜 예

| 나쁜 예 | 좋은 예 |
|---------|---------|
| Docker는 컨테이너 기반 가상화 플랫폼이다. | Docker는 컨테이너 기반 가상화 플랫폼이에요. |
| 본 문서에서는 네트워킹을 다룬다. | 이번 글에서는 네트워킹을 다뤄볼게요. |
| 상기 방법을 적용하면 된다. | 위 방법을 적용하면 돼요. |
| 필자는 이 방식을 선호한다. | 저는 이 방식을 선호해요. |

### 금지 표현

- "본 문서", "상기", "하기" 등 공문서체
- "필자" → "저"로 대체
- 불필요한 경어 중첩 ("~하시겠습니다" 등)
- 영어 원문 번역투 ("그것은 ~이다", "~하는 것은 중요하다")

## 글 구성

```
도입 (1-2문단): 왜 이 주제가 중요한지, 이 글에서 뭘 다루는지

## 본문 섹션 1
설명 + 코드/예시

## 본문 섹션 2
...

## 마무리 (선택)
핵심 요약 또는 다음 단계 안내
```

### 제목

- 명사형 종결 ("Docker 네트워킹 설정") 또는 의문형 ("왜 gRPC를 써야 할까?")

## 검색 친화 구조 (SEO/AEO)

섹션 제목을 검색 질문에 대응시키면 검색 스니펫과 AI 답변 엔진(AEO) 인용에 유리합니다.
단, 모든 섹션에 강제하면 FAQ 스팸처럼 읽히므로 **선별 적용**합니다.

### 질문형 섹션 제목 (권장)

- 독자가 실제 검색할 만한 질문을 h2/h3로: "좋은 커밋 규칙은?", "커밋 규칙은 어떻게 정할까요?"
- **글당 1개만** — 검색 의도가 가장 분명한 섹션(방법/이유/비교/트러블슈팅) 하나를 골라 적용
- 일기/근황 섹션("요즘 개발 상황")은 명사형 유지 — 글의 결이 우선, 어울리지 않으면 전환하지 않음

### 직답 우선 (answer-first)

- 질문형 제목 바로 아래 첫 1-2문장에서 답을 먼저 제시하고, 배경/코드/세부는 그 뒤에 풀어요
- 직답 없이 서론으로 시작하는 질문 섹션 금지 (스니펫/AEO 추출 실패)

예:

```
## 좋은 커밋 규칙은?

결론부터 말하면 "하나의 커밋 = 하나의 의도"예요. 이것만 지켜도 리뷰와 롤백이 쉬워져요.
이제 이 원칙을 팀에 어떻게 적용했는지 보여드릴게요.
```

## 독자 수준 태깅

글마다 독자 수준이 다를 수 있으므로, 프론트매터에 `level` 필드를 추가합니다:

| level | 대상 | 설명 스타일 |
|-------|------|------------|
| `beginner` | 주니어/입문자 | 용어 풀이 포함, 배경 설명 충분히 |
| `intermediate` | 중급 개발자 | 기초 생략, 실무 관점 중심 |
| `advanced` | 시니어/전문가 | 트레이드오프, 깊은 분석 중심 |

## description 작성 규칙

- 글의 핵심 가치를 한 문장으로, 150-160자
- "이 글에서는 ~를 다룹니다" 패턴 금지 → 구체적 내용 요약
- 나쁜 예: "이 글에서는 Docker를 설명합니다"
- 좋은 예: "Docker 브릿지 네트워크와 오버레이 네트워크의 차이점, 실무 설정 방법을 정리했어요"
